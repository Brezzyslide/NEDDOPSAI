# NeedsOps Digital Workforce — Professional Design Lifecycle

> **Version:** 1.0.0  
> **Status:** Founder-Approved  
> **Classification:** Tier 1 Governance Artefact  
> **Scope:** All current and future NeedsOps AI Employees  
> **Supersedes:** N/A — inaugural version

---

## Purpose

This document defines the complete professional design lifecycle that every NeedsOps AI Employee passes through — from the initial founder workshop through to production deployment and ongoing operation.

It defines the stages, the artefacts produced at each stage, the responsible parties, and the quality gates that must be cleared before progression.

No stage may be skipped. No artefact may be omitted. No specialist may be activated without completing this lifecycle.

---

## The Lifecycle

```
┌─────────────────────────────────────────────────────────────────┐
│                    STAGE 1 — FOUNDER WORKSHOP                    │
│                                                                  │
│  Founder leads a structured session exploring:                   │
│  • The professional domain this specialist will operate in       │
│  • The participant population they will serve                    │
│  • The regulatory and legislative environment                    │
│  • The professional standard expected                            │
│  • The ethical obligations specific to this role                 │
│  • The capabilities this specialist must hold                    │
│  • The boundaries this specialist must respect                   │
│  • The escalation obligations specific to this role              │
│                                                                  │
│  Output: Workshop notes and founder thinking (not public)        │
│  Owner: Founder                                                  │
└────────────────────────────┬────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│               STAGE 2 — SHARED GOVERNANCE FRAMEWORK             │
│                                                                  │
│  Workshop findings are assessed against the existing Shared      │
│  Professional Governance Framework:                              │
│                                                                  │
│  • Professional Constitution (values, ethics, standards)         │
│  • Executive Operating System (executive roles only)            │
│  • Universal Decision Hierarchy (all specialists)               │
│                                                                  │
│  Any gap in the shared framework is identified and resolved      │
│  before specialist design begins.                                │
│                                                                  │
│  Output: Confirmation that the shared framework is complete      │
│  Owner: Founder + Architecture                                   │
└────────────────────────────┬────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│               STAGE 3 — PROFESSIONAL DESIGN BRIEF               │
│                                                                  │
│  Architecture structures the founder's workshop knowledge into   │
│  the Professional Design Brief template — 26 sections covering:  │
│                                                                  │
│  • Identity and role definition                                  │
│  • Professional domain and population scope                      │
│  • Regulatory and legislative context                            │
│  • Capability architecture                                       │
│  • Authority matrix                                              │
│  • Escalation framework                                          │
│  • Quality and evidence standards                                │
│  • Professional ethics (role-specific)                           │
│  • Collaboration model                                           │
│  • Prohibited behaviours and hard stops                          │
│  • Constitutional alignment verification                         │
│                                                                  │
│  Output: Professional Design Brief (draft)                       │
│  Owner: Architecture (content from founder)                      │
└────────────────────────────┬────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│             STAGE 4 — PROFESSIONAL EVIDENCE REGISTER            │
│                                                                  │
│  For each significant professional claim in the Design Brief:   │
│  • The evidence basis is identified                             │
│  • Quality is assessed (legislation, peer-reviewed, guidance,   │
│    professional standard, expert opinion, working assumption)    │
│  • Gaps in the evidence base are documented                     │
│  • Areas of professional uncertainty are flagged                │
│                                                                  │
│  Output: Professional Evidence Register                          │
│  Owner: Subject Matter Expert + Architecture                     │
└────────────────────────────┬────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│                STAGE 5 — FOUNDER APPROVAL (BRIEF)               │
│                                                                  │
│  The founder reviews and approves the Professional Design Brief  │
│  and the Evidence Register.                                      │
│                                                                  │
│  Review confirms:                                                │
│  • The Brief accurately reflects the founder's professional      │
│    intent for this specialist                                    │
│  • No section contradicts the constitutional framework           │
│  • The evidence quality is declared and accepted                 │
│  • The capability and authority scope is correct                 │
│                                                                  │
│  ✅ QUALITY GATE — Brief must be founder-approved before         │
│     Employee File authorship begins.                             │
│                                                                  │
│  Output: Approved Professional Design Brief                      │
│  Owner: Founder                                                  │
└────────────────────────────┬────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│                  STAGE 6 — EMPLOYEE FILE                        │
│                                                                  │
│  Architecture authors the Employee File from the approved        │
│  Design Brief — structured across 12 sections:                  │
│                                                                  │
│  §1  Identity and Core Purpose                                   │
│  §2  Professional Domain                                         │
│  §3  Constitutional Alignment                                    │
│  §4  Core Capabilities                                           │
│  §5  Decision Framework                                          │
│  §6  Communication Standards                                     │
│  §7  Relationship Model                                          │
│  §8  Quality Standards                                           │
│  §9  Ethics and Escalation                                       │
│  §10 Hard Stops and Boundaries                                   │
│  §11 Professional Development Philosophy                         │

│                                                                  │
│  Output: Employee File (draft)                                   │
│  Owner: Architecture                                             │
└────────────────────────────┬────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│               STAGE 7 — CAPABILITY CATALOGUE                    │
│                                                                  │
│  For each capability identified in the Employee File:           │
│  • A Capability Definition is authored                          │
│  • Conditions of use are specified                              │
│  • Evidence requirements are defined                            │
│  • Refusal and escalation criteria are defined                  │
│  • Integration with other capabilities is documented            │
│                                                                  │
│  Output: Capability Catalogue (one definition per capability)    │
│  Owner: Architecture + Subject Matter Expert                     │
└────────────────────────────┬────────────────────────────────────┘
                             │
                             ▼

│                 STAGE 8 — AUTHORITY MATRIX                      │
│                                                                  │

│  • What decisions the specialist can make independently          │
│  • What requires consultation before deciding                    │
│  • What must be escalated for decision by a higher authority     │
│  • What the specialist must never do regardless of instruction   │
│  • Approval thresholds where applicable                          │
│                                                                  │
│  Output: Authority Matrix                                        │
│  Owner: Architecture + Founder review                            │
└────────────────────────────┬────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│          STAGE 9 — RUNTIME COMPILATION AND VALIDATION           │
│                                                                  │
│  Engineering compiles the Runtime Manifest from:                │

│  • Employee File identity and capability summary                 │
│  • Capability Catalogue identifiers                              │
│  • Authority codes from the Authority Matrix                    │
│  • Hard stops and boundary conditions                            │
│                                                                  │
│  Architecture validates the compiled manifest against:          │
│  • The approved Employee File                                    │
│  • The Authority Matrix                                          │
│  • The constitutional framework                                  │
│                                                                  │
│  ✅ QUALITY GATE — Manifest must be validated before testing.    │
│                                                                  │
│  Output: Validated Runtime Manifest                              │

                             │
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│               STAGE 10 — FOUNDER APPROVAL (FULL)                │
│                                                                  │
│  The founder reviews and approves:                               │
│  • The Employee File                                             │
│  • The Capability Catalogue                                      │
│  • The Authority Matrix                                          │
│  • The Runtime Manifest summary                                  │
│                                                                  │
│  ✅ QUALITY GATE — Founder approval required before testing.     │
│                                                                  │
│  Output: Approved specialist design package                      │
│  Owner: Founder                                                  │
└────────────────────────────┬────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│                     STAGE 11 — TESTING                          │
│                                                                  │
│  Engineering executes the specialist test suite:                │
│  • Unit tests for all specialist services                        │
│  • Integration tests for execution pipeline                      │
│  • Scenario tests derived from the Capability Catalogue          │
│  • Boundary tests against the Authority Matrix                   │
│  • Hard stop tests — verifying prohibited behaviours refuse      │
│  • Constitutional alignment tests                                │
│                                                                  │
│  Architecture reviews test results for professional quality:     │
│  • Does the specialist's output meet the professional standard?  │
│  • Are escalation and refusal behaviours correct?                 │
│  • Does the confidence calibration match the evidence?           │
│                                                                  │
│  ✅ QUALITY GATE — All tests passing before production.          │
│                                                                  │
│  Output: Test results and professional quality review            │
│  Owner: Engineering (tests) + Architecture (quality review)      │
└────────────────────────────┬────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│                    STAGE 12 — PRODUCTION                        │
│                                                                  │
│  The specialist is activated in the production environment.      │
│                                                                  │
│  Ongoing:                                                        │
│  • Performance is monitored against the Design Brief standard    │
│  • Issues are raised through the change governance process       │
│  • Changes to Employee Files trigger a return to Stage 6+        │
│  • Constitutional changes trigger a full programme review        │
│                                                                  │
│  Output: Active specialist in production                         │
│  Owner: Engineering (operations) + Architecture (governance)     │
└─────────────────────────────────────────────────────────────────┘
```

## Stage Responsibilities

### Founder

| Stage | Responsibility |
|-------|---------------|
| 1 — Workshop | Leads the session. Provides the professional knowledge. Owns the output. |
| 5 — Brief Approval | Reviews and approves the Professional Design Brief and Evidence Register. |
| 10 — Full Approval | Reviews and approves the complete design package before testing. |
| Ongoing | Approves any substantive change to a constitutional document or Employee File. |

### Subject Matter Expert

| Stage | Responsibility |
|-------|---------------|
| 4 — Evidence Register | Provides or validates the professional evidence basis for each significant claim. |
| 7 — Capability Catalogue | Reviews each Capability Definition for professional accuracy and completeness. |
| 11 — Testing | Reviews test scenarios and professional quality outcomes. |

### Architecture

| Stage | Responsibility |
|-------|---------------|
| 2 — Shared Framework | Confirms the shared framework is complete before specialist design begins. |
| 3 — Design Brief | Structures founder knowledge into the Brief template. |
| 6 — Employee File | Authors the Employee File from the approved Brief. |
| 7 — Capability Catalogue | Authors Capability Definitions from the Employee File. |
| 8 — Authority Matrix | Defines the specialist's authority structure. |
| 9 — Validation | Validates the Runtime Manifest against the approved design package. |
| 11 — Testing | Reviews professional quality of test outcomes. |

### Engineering

| Stage | Responsibility |
|-------|---------------|
| 9 — Compilation | Compiles the Runtime Manifest from the approved design package. |
| 11 — Testing | Writes and executes all automated test suites. |
| 12 — Production | Deploys and operates the specialist in the production environment. |

### Testing

| Stage | Responsibility |
|-------|---------------|
| 11 — Testing | Independently executes and signs off on the testing stage quality gate. |

## Quality Gates Summary

| Gate | Stage | Required Before |
|------|-------|----------------|
| **Brief Approval** | Stage 5 | Employee File authorship |
| **Manifest Validation** | Stage 9 | Founder full approval |
| **Founder Full Approval** | Stage 10 | Testing |
| **Testing Complete** | Stage 11 | Production |

No gate may be bypassed. Where a gate is not cleared, the work returns to the preceding stage for resolution.

---

## Change Governance

Changes to active specialists after production deployment follow the same lifecycle — beginning at the stage appropriate to the nature of the change:

| Change Type | Re-enter at Stage |
|-------------|------------------|
| Constitutional document change | Stage 1 (full programme review) |
| Employee File change | Stage 6 |
| Capability addition | Stage 7 |
| Authority change | Stage 8 |
| Runtime Manifest change | Stage 9 |
| Bug fix (no design change) | Stage 11 |

All changes require architecture review. Substantive changes require founder approval.
