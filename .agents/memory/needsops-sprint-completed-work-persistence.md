---
name: NeedsOps Completed Work Version Persistence Fix
description: Three root-cause bugs fixed — FK insert order, incomplete-marker regex, rule-based fallback saved as real work.
---

## Root cause 1 — FK violation: version inserted before parent

`createDraft` in `completedWorkService.ts` inserted `completed_work_versions` FIRST, before `completed_work`.
`completed_work_versions.completed_work_id` has a FK → `completed_work.id` (onDelete: cascade).
PostgreSQL immediately rejects the insert with error 23503.

**Fix:** Wrap both inserts in `db.transaction()`. Insert **parent first**, then version. Transaction rolls back both on any failure — no orphaned rows.

**Why:** The child FK must reference an existing parent row. The original code had the order reversed — likely a copy-paste from `addVersion` which doesn't need to create the parent.

**How to apply:** Any future version of createDraft must keep this order inside the transaction: (1) completedWorkTable insert, (2) completedWorkVersionsTable insert.

## Root cause 2 — Incomplete marker regex missed colon-prefix form

The blueprint execution addendum instructs the specialist: "Mark sections as [INCOMPLETE: description]".
The rule-based fallback uses exactly this form: `[INCOMPLETE: This section requires AI generation...]`.

But `reviewCompleteness` and `reviewMissingInformation` only matched the exact bracket form `[INCOMPLETE]` — not `[INCOMPLETE: any text]`.

**Fix:** Changed both regexes from `/\[INCOMPLETE\]|\[MISSING\]|\[TODO\]/` to `/\[INCOMPLETE(?::[^\]]+)?\]|\[MISSING(?::[^\]]+)?\]|\[TODO(?::[^\]]+)?\]/gi`.
Applied the same extension to the 5-marker regex in `reviewMissingInformation`.

**Why:** The colon-prefix is the form actually generated by both the LLM (following the blueprint contract) and the rule-based fallback. The original regex was written for a simpler era before the blueprint addendum was introduced.

## Root cause 3 — Rule-based fallback content saved as real Completed Work

When `AI_PROVIDER` is unset (or provider returns empty/fallback), `generateDraft` silently returned a stub with `[INCOMPLETE: ...]` headers. The pipeline then ran the stub through self-review and called `createDraft`, persisting it as real specialist work.

**Fix:** Introduced `FallbackDraftError extends Error`. `generateDraft` now throws it instead of returning fallback content. The catch block in `executeWork` special-cases it to return `{ outcome: "configuration_failure" }` — never calls `createDraft`.

**Why:** A rule-based stub is not professional work. Saving it misleads users into thinking the specialist ran. The error is explicitly retryable (once `AI_PROVIDER` is configured).

**How to apply:** Any new code path that can fall back to rule-based content must throw `FallbackDraftError` rather than return the stub. `configuration_failure` is a valid `ExecutionOutcome`.
