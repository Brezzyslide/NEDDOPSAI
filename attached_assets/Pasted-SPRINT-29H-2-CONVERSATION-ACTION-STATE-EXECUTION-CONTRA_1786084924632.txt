Implement the correction proven necessary by the Sprint 29H.1 verification.

OBJECTIVE

Make Workforce Chat correctly distinguish:

1. VIEW existing completed work
2. DISCUSS/SUMMARISE existing completed work
3. APPROVE existing work
4. REVISE existing work
5. RERUN work using current evidence
6. CREATE genuinely new work

A prior completedWorkId must provide historical context.
It must NOT automatically suppress a legitimate new execution.

PART A — REMOVE THE UNCONDITIONAL COMPLETED SHORT-CIRCUIT

Replace:

if (s.completedWorkId) return "completed"

with deterministic action-state resolution that considers:

- requestedTaskAction
- conversationMode
- explicit rerun/new/revise intent
- completed work status
- current task state
- current specialist eligibility where relevant

Existing completed work should suppress execution only for intents that are
actually asking to view, discuss, summarise, inspect or act on that existing work.

Examples:

"Show me the review"
→ existing work

"What were the findings?"
→ existing work

"Approve the review"
→ approval/status action against existing work

"Revise the review..."
→ revision execution

"Review this again using latest evidence"
→ new execution

"Replace the old review with a new Operations Manager review"
→ new execution, preserve old work

"Produce a new Improvement Plan"
→ new task/execution

PART B — CREATE A DETERMINISTIC ACTION DECISION

Introduce one typed platform decision after CoS classification.

Example:

ConversationActionDecision {
  action:
    | "respond"
    | "view_existing"
    | "summarise_existing"
    | "approve_existing"
    | "revise_existing"
    | "rerun_existing"
    | "create_new_work";

  completedWorkId?: string;
  taskId?: string;

  shouldCreateTask: boolean;
  shouldDispatchSpecialist: boolean;

  reasonCode: string;
}

The LLM may classify semantic intent.

The platform must deterministically decide what operation follows.

Do NOT allow shouldCreateTask or shouldDispatchSpecialists to remain
informational fields with no consumer.

PART C — WIRE THE ACTIONS

create_new_work
→ existing task creation/dispatch path
→ UEE

rerun_existing
→ create new execution/run using current routing/evidence
→ preserve historical completed work
→ UEE

revise_existing
→ existing revision mechanism
→ reference source completedWorkId
→ UEE

approve_existing
→ use actual persisted completed_work status
→ only perform approval when transition is valid

view_existing / summarise_existing
→ no specialist execution

PART D — FIX COMPLETED-WORK FACTUAL CONTEXT

When historical completed work is relevant, buildActionStateSection must expose
grounded persisted metadata:

- completedWorkId
- status
- title
- primarySpecialist
- createdAt
- approvedAt where applicable
- source taskId
- qualityScore if available

Do NOT present task_specialists as evidence of who produced completed work.

Keep these concepts distinct:

assignedSpecialists = who was assigned/intended
primarySpecialist = who actually produced persisted completed work

PART E — ATTRIBUTION INTEGRITY

Add a specialist attribution integrity rule.

If CoS says:

"Operations Manager completed..."
"Executive Assistant produced..."
"X specialist reviewed..."

the named specialist must match persisted execution/completed-work provenance.

Otherwise:
- reject/correct the claim
- use persisted primarySpecialist
- or omit specialist attribution

Completed state must NOT bypass this integrity rule.

PART F — STATUS-AWARE APPROVAL

CoS must distinguish at minimum:

draft
awaiting_approval
approved
rejected / changes_requested if supported

"Approve the review" against an already-approved record must NOT claim that an
approval occurred.

Return the actual persisted status.

No service outside UEE performs specialist AI execution.

Existing completed work is historical state, not an execution lock.
