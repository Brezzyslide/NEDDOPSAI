# NeedsOps AI+

## Sprint 1: Organisations, Identity and Tenant Security

Sprint 0 is approved and complete.

Proceed with Sprint 1 only.

Do not begin Sprint 2 or any later sprint until Sprint 1 has been implemented, tested, documented and approved.

The purpose of Sprint 1 is to create the secure identity, organisation and tenant foundation that every future NeedsOps AI+ feature will depend on.

NeedsOps AI+ is a multi-tenant AI operations and workforce platform.

Every customer organisation must have its own secure tenant boundary.

Users may belong to one or more organisations, but they must never access data belonging to an organisation unless they have an active membership in that organisation.

Authentication confirms who the user is.

Membership confirms which organisations the user belongs to.

Permissions determine what the user may do.

Entitlements determine what the organisation’s subscription includes.

These concepts must remain separated throughout the architecture.

# Non-Negotiable Security Principles

The following rules must be enforced:

1. Never trust a tenant ID supplied by the frontend.
2. Every protected request must resolve the authenticated user on the server.
3. Every tenant-scoped request must verify active organisation membership.
4. Every tenant-owned query must include the resolved tenant ID.
5. A user must not access another tenant by changing a URL, request body, query string or header.
6. Role checks must happen on the server.
7. Session tokens must not expose secrets.
8. Passwords must never be stored directly.
9. Authentication secrets must remain server-side.
10. Every membership and role change must be audited.
11. All invitation tokens must expire.
12. Invitation tokens must be single use.
13. Suspended users and memberships must lose access immediately.
14. Deleted or inactive organisations must not allow operational access.
15. Audit logs must not contain passwords, session tokens or raw secrets.

Create automated tests for these boundaries.

# Tenant Context

Create a server-side tenant context service and middleware.

A protected request must resolve:

```typescript
interface TenantContext {
  userId: string;
  externalUserId: string;
  tenantId: string;
  membershipId: string;
  role: MembershipRole;
  permissions: Permission[];
}
```

Tenant resolution may use:

* organisation slug in the route
* active organisation stored in the session
* an organisation selector

But the server must verify that the authenticated user has an active membership in the resolved organisation.

Reject requests where:

* user is unauthenticated
* email is unverified
* user is suspended
* tenant is inactive
* membership is missing
* membership is suspended
* required permission is missing

Return consistent error responses.

Suggested error codes:

```text
AUTHENTICATION_REQUIRED
EMAIL_VERIFICATION_REQUIRED
USER_SUSPENDED
TENANT_NOT_FOUND
TENANT_INACTIVE
MEMBERSHIP_REQUIRED
MEMBERSHIP_SUSPENDED
PERMISSION_DENIED
```

# Tenant Isolation

Update all tenant-owned database services so they require tenant context.

Avoid functions like:

```typescript

```

Prefer:

```typescript
getTaskById({
  tenantId,
  taskId
})
```

Even where task functionality is not yet active, establish this pattern in repositories and services.

Create tenant-scoped repository helpers.

Add tests proving:

1. Tenant A cannot retrieve Tenant B organisation.
2. Tenant A cannot retrieve Tenant B membership.
3. A user cannot switch to an organisation without membership.
4. Changing a tenant slug in the URL does not grant access.
5. A suspended membership is rejected.
6. A viewer cannot perform an administrator action.
7. An administrator in Tenant A has no permissions in Tenant B unless separately assigned there.
