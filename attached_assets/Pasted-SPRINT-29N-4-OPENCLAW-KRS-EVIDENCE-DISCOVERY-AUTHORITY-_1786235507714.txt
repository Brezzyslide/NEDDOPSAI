SPRINT 29N.4 — OPENCLAW + KRS EVIDENCE DISCOVERY & AUTHORITY PROOF GATE

INVESTIGATION / CONTROLLED PROOF ONLY. DO NOT REPLACE KRS, UEE OR THE CURRENT CLOUD EXECUTION PATH.

Objective

Determine whether OpenClaw should become an intelligent evidence-discovery layer alongside KRS for both Cloud and Hybrid execution.

The architecture under consideration is:

User → CoS → execution classification → specialist DNA + tenant/governance context → KRS + OpenClaw evidence discovery → NeedsOps authority validation → canonical EvidencePack → OpenAI reasoning → claim/provenance validation → permitted OpenClaw actions/artifact operations → Completed Work → approval/audit/notification

The proposed responsibility boundary is:

NeedsOps decides and governs.

KRS determines what evidence may be trusted and relied upon.

OpenClaw discovers, locates and reads resources.

OpenAI performs professional reasoning.

OpenClaw may subsequently perform authorised actions.

Do not assume this architecture is better. Prove or reject it.

A — Establish the evidence contract

Design a canonical CandidateEvidence contract for evidence discovered by OpenClaw.

At minimum it should carry:

organizationId

executionId

taskId where applicable

specialistCode

runtimeLocation: cloud | hybrid

sourceId where known

sourceVersionId where known

sourceUri/resourceId

sourceType

sourceTitle

sourceOwner/provider

retrievedAt

sourceModifiedAt/version where available

passage

passageLocation — page/section/paragraph/range where available

contentHash

discoveryReason

retrievalMethod

OpenClawConfidence if available

OpenClaw confidence must never equal authority.

OpenClaw returns candidate evidence, not trusted evidence.

B — KRS acceptance gate

Design the transformation:

CandidateEvidence → NeedsOps/KRS validation → AcceptedEvidence → EvidencePack

KRS/NeedsOps must determine:

tenantVerified

accessPermitted

sourceIdentityVerified

canonicalSourceId

canonicalVersionId

authorityClass

authorityVerified

currentVersionVerified

effectiveDateVerified

integrityVerified

sensitivityPermitted

evidenceStatus

Only accepted evidence may enter the canonical EvidencePack for evidence-bearing professional claims.

Reuse the existing KRS, source/version, evidence snapshot and claim provenance architecture. Do not build a second authority system.

C — Internal organisational source rules

Test what happens when OpenClaw discovers:

1. approved/current Library document
2. superseded document
3. unapproved document
4. duplicate document
5. newer local document unknown to Library
6. document belonging to another tenant
7. restricted/sensitive document
8. document whose title differs materially from the user’s terminology

A file being found by OpenClaw must not make it organisational source of truth.

Determine exactly how KRS resolves each case.

D — External source-of-truth model

OpenClaw may discover evidence through the web or external providers.

Design how NeedsOps distinguishes:

* official legislation
* regulator
* government authority
* recognised standard/standards body
* contractual/external authority
* professional guidance
* reputable secondary source
* general web source
* unknown/untrusted source

Investigate whether NeedsOps needs an AuthorityRegistry or equivalent existing structure mapping:

source/domain/provider → authorityType → jurisdiction/domain → permitted claim types → trust/authority status

Do not automatically trust a website because OpenClaw says it is authoritative.

Determine how official-source identity should be verified.

This must integrate with Sprint 29K’s existing external_requirement rule requiring external_authority.

F — Test agentic retrieval specifically

This is important.

Determine whether OpenClaw adds value because it can perform multi-step investigation, rather than simply another search.

Example:

User asks to review Complaints Management.

OpenClaw finds the Complaints Policy.

That document references an Escalation Procedure.

OpenClaw follows the reference and locates it.

The Escalation Procedure refers to Incident Management.

OpenClaw discovers that source.

NeedsOps then independently determines which discovered resources are authorised/current and may enter the EvidencePack.

Compare this against one-shot KRS retrieval.

Establish whether this materially improves evidence completeness.

discovered → tenant verified → fingerprint/hash → identity resolution → ingestion → authority/currentness evaluation → accepted/review_required → EvidencePack

Determine when auto-acceptance is safe under the Library auto-ingestion rules already implemented and when human governance is required.

L — Failure and adversarial tests

Explicitly test:

* OpenClaw fabricates a source
* incorrect tenant ID
* valid source from wrong tenant
* stale document
* altered document after retrieval
* invented supporting passage
* valid URL but wrong authority
* malicious webpage claiming to be regulator
* conflicting internal documents
* OpenClaw confidence 0.99 on an unapproved source
* OpenClaw fails midway through investigation

Expected principle:

Discovery failure may reduce recall. It must never lower the authority standard.

M — Decide whether OpenClaw actually belongs in evidence retrieval

Answer explicitly:

1. Does OpenClaw retrieve materially more relevant evidence than current KRS?
2. Does that remain true after KRS semantic/vector retrieval is properly enabled?
3. Is OpenClaw particularly better at multi-document/agentic discovery?
4. Does OpenClaw improve external web authority discovery?
5. Can NeedsOps reliably validate what OpenClaw discovers?
6. Does combined retrieval outperform either system alone?
7. What is the latency/cost penalty?
8. Should OpenClaw run for every evidence-bearing task or only when KRS confidence/coverage is insufficient?
9. Should OpenClaw ever directly place evidence into EvidencePack?
10. Should OpenClaw ever determine organisational source of truth?

Questions 9 and 10 should normally be NO unless the existing NeedsOps authority guarantees can be mathematically/technically preserved.

N — Architecture decision

Compare:

N1 — KRS only

KRS discovers and governs.

N2 — OpenClaw replaces KRS retrieval

OpenClaw discovers; NeedsOps only validates.

N3 — Parallel retrieval

KRS + OpenClaw independently discover → NeedsOps validates/merges → EvidencePack.

N4 — Escalation retrieval

KRS first → OpenClaw invoked when evidence coverage/confidence is inadequate or deeper investigation is required → NeedsOps validates → EvidencePack.

Recommend the best architecture based on evidence, not preference.

Most importantly:

Do not confuse “OpenClaw found it” with “NeedsOps trusts it.”

NO PRODUCTION IMPLEMENTATION. STOP AFTER THE REPORT.

And there is one architectural possibility I particularly want this test to settle.

We may discover that running OpenClaw every time is unnecessary. If properly activated hybrid KRS gets the obvious evidence in 200–500 ms, use it. Then OpenClaw becomes the deeper investigator when KRS coverage is weak, documents reference other documents, an absence needs proving, or external evidence needs finding.

That could give you the best combination: fast when the answer is straightforward, investigative when the work genuinely requires it.

If the bake-off instead shows parallel OpenClaw + KRS consistently produces substantially better evidence without unacceptable latency, then we make parallel discovery the evidence-bearing default.

Either result is good. We stop guessing and let the system prove which architecture deserves to survive. 😀
