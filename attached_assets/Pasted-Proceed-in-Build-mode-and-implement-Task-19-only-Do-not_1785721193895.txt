2. AUTOMATIC INGESTION TRIGGER
────────────────────────────────────────

When a supported knowledge source upload is successfully completed:

- create or reuse an ingestion job
- enqueue it automatically
- do not require a user to manually call the ingest endpoint
- preserve idempotency
- do not create duplicate active jobs for the same source version
- do not enqueue revoked, deleted, archived, or superseded sources
- do not process a source before upload completion
- record an audit event

The manual ingest endpoint may remain for retry, repair, and administrative use.

3. QUEUE ABSTRACTION
────────────────────────────────────────

Create a provider-neutral queue interface.

Suggested operations:

- enqueue(job)
- claimNext(workerId)
- heartbeat(jobId, workerId)
- complete(jobId, workerId)
- fail(jobId, workerId, error)
- release(jobId, workerId)
- retry(jobId)
- cancel(jobId)
- getDepth()
- getOldestQueuedAt()

Do not tie the core ingestion pipeline directly to one queue provider.

Implement:

- database-backed queue for local development and Replit
- AWS-ready adapter interface for SQS
- clear provider selection through environment variables

Suggested environment variable:

KNOWLEDGE_QUEUE_PROVIDER=database

Future production value:

KNOWLEDGE_QUEUE_PROVIDER=sqs

Do not claim SQS is active unless it is actually configured and tested.

────────────────────────────────────────
4. DATABASE QUEUE WORKER
────────────────────────────────────────

Implement a durable database-backed worker.

Requirements:

- claim jobs atomically
- use row locking or equivalent protection
- prevent two workers from processing the same job
- assign workerId
- record claimedAt
- record heartbeatAt
- record leaseExpiresAt
- increment attempt count
- support retry delay
- support cancellation
- support graceful shutdown
- support safe restart
- preserve tenant isolation
- do not hold long database transactions during extraction or embedding

Add schema fields or a worker-leases table if required.

────────────────────────────────────────
5. WORKER PROCESS
────────────────────────────────────────

Create a dedicated worker entry point rather than running heavy ingestion inside the HTTP request.

Examples:

- artifacts/api-server/src/workers/knowledgeIngestionWorker.ts
- a separate workspace package if that better fits the codebase

Worker behaviour:

1. start
2. register worker identity
3. poll queue
4. claim one job
5. start heartbeat
6. run ingestion pipeline
7. complete or fail job
8. apply retry policy
9. continue polling
10. stop gracefully on SIGTERM or SIGINT

The worker must not block API traffic.

For local and Replit development, allow the worker to run as:

- a separate process
- or an explicitly enabled in-process development worker

Production should prefer a separate worker process.

────────────────────────────────────────
6. RETRY POLICY
────────────────────────────────────────

Implement retry categories.

Retryable examples:

- temporary storage failure
- provider timeout
- provider rate limit
- temporary database issue
- transient network failure
- worker crash
- expired lease

Non-retryable examples:

- unsupported file type
- corrupted document
- encrypted document without password
- source revoked
- source deleted
- invalid version state
- permanent extraction failure
- policy restriction preventing embedding

Suggested retry behaviour:

- exponential backoff
- jitter
- configurable maximum attempts
- safe terminal failure state

Record:

- attempt count
- nextAttemptAt
- lastErrorCode
- lastSafeErrorMessage
- lastFailedAt

Do not store raw provider errors containing secrets or document content.

────────────────────────────────────────
7. STUCK JOB AND LEASE RECOVERY
────────────────────────────────────────

Implement stuck-job recovery.

A job is considered abandoned when:

- status is processing
- lease has expired
- heartbeat is stale
- worker no longer owns the lease

Recovery behaviour:

- release the stale lease
- return retryable jobs to queued
- increment recovery count
- preserve the previous error context
- do not create a duplicate job
- audit the recovery

Add a periodic sweeper.

Suggested environment variables:

KNOWLEDGE_WORKER_HEARTBEAT_MS
KNOWLEDGE_WORKER_LEASE_MS
KNOWLEDGE_WORKER_POLL_MS
KNOWLEDGE_WORKER_MAX_ATTEMPTS
KNOWLEDGE_WORKER_SWEEP_MS

Provide safe defaults.

────────────────────────────────────────
8. CANCELLATION
────────────────────────────────────────

Cancellation must work for:

- queued jobs
- claimed jobs
- jobs between stages

Requirements:

- cancellation request stored durably
- worker checks cancellation between pipeline stages
- no new chunks written after cancellation is observed
- partially written chunks are rolled back or marked invalid
- embeddings are not retained for cancelled content
- final status becomes cancelled
- audit event created

Do not claim hard cancellation during an active third-party API request unless the provider genuinely supports it.

9. IDEMPOTENCY

- repeated upload completion does not duplicate processing
- repeated queue enqueue is safe
- repeated worker completion is safe
- repeated failure handling is safe
- completed jobs are not processed again unless explicitly reprocessed
- reprocessing creates a clear new attempt or job lineage

Add database constraints where appropriate.
