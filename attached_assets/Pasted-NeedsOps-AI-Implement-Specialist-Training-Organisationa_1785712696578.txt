NeedsOps AI+ — Implement Specialist Training, Organisational Knowledge, and RAG

Proceed with implementation.

Use the existing NeedsOps architecture as the foundation. Do not rebuild the specialist runtime, Business Discovery, organisation memory, or specialist configuration systems from scratch.

The purpose of this sprint is to let each SaaS customer properly teach its AI workforce how the organisation works, including:

- organisational language and terminology
- writing tone and style
- internal policies
- procedures and playbooks
- approved examples
- escalation rules
- specialist responsibilities
- approval requirements
- current and superseded document versions
- specialist-specific knowledge

The target experience is:

Choose specialist
→ define responsibilities and boundaries
→ define language and writing style
→ add approved knowledge sources
→ upload policies, procedures, playbooks, and examples
→ choose who may use each source
→ process and index the material
→ test the specialist
→ review retrieved evidence
→ approve the specialist as ready

The first end-to-end reference specialist must be:

Incident Management Specialist

The architecture must remain reusable for every NeedsOps specialist.

PRIMARY DESIGN PRINCIPLES
────────────────────────────────────────

1. Separate structured configuration from retrieved knowledge.

Structured configuration includes:

- preferred writing style
- role instructions
- escalation contacts
- approval rules
- business hours
- language conventions
- authorised systems
- specialist goals

Retrieved knowledge includes:

- policy sections
- procedure steps
- playbook content
- approved examples
- templates
- internal guidance
- legislation references
- previous approved work products

Do not put all knowledge into one large JSON field.

2. Knowledge must be scoped.

Do not solve specialist knowledge by adding only one nullable specialistId field.

Support these scope types:

- organisation
- workforce
- specialist
- department
- location
- task_type

Use a durable scope model such as:

- scopeType
- scopeId

A knowledge source may have more than one scope where appropriate.

3. Retrieval must be permission-aware and version-aware.

The most semantically similar passage is not automatically the correct passage.

Every retrieval must filter by:

- organisation
- authorised specialist or workforce
- user role and permission
- source approval status
- document lifecycle status
- effective date
- superseded status
- sensitivity classification
- task purpose
- location or department where relevant

4. Preserve lexical retrieval.

Do not discard the existing deterministic keyword retrieval.

Build hybrid retrieval combining:

- lexical keyword relevance
- semantic vector similarity
- importance
- recency
- pinned or mandatory knowledge
- authoritative source priority

5. Outputs must be grounded.

When a specialist uses retrieved knowledge, the output must retain source references.

Example:

“Based on Incident Management Policy v3.2, section 6.4, effective 12 June 2026…”

Do not allow the specialist to present unsupported statements as company policy.

PHASE 4 — TEXT EXTRACTION AND INGESTION
────────────────────────────────────────

Build an asynchronous ingestion pipeline.

Pipeline:

Upload
→ validate
→ extract text
→ classify sections
→ normalise
→ chunk
→ calculate lexical index
→ generate embeddings
→ store chunks
→ mark review required
→ human approval
→ available for retrieval

Requirements:

- idempotent ingestion
- retryable jobs
- ingestion status
- failure reason
- cancellation
- source checksum
- no duplicate reprocessing for identical versions
- document page and heading metadata
- removal of repeated headers and footers where practical
- preservation of section titles
- safe handling of empty or scanned PDFs
- OCR must be behind a separate optional adapter
- do not silently claim OCR success when only image pages were found

Initial extraction libraries should be well-maintained and suitable for server use.

Keep the extraction interface provider-neutral.

Chunking requirements:

- preserve logical policy sections
- prefer heading-aware and paragraph-aware chunking
- retain modest overlap
- store source offsets or page references
- respect model token limits
- do not split tables or numbered procedures carelessly where avoidable
- assign stable chunk hashes
- support re-chunking when the strategy changes

Do not mark content as retrievable until an authorised user approves the source or version.

- recency
