Sprint 9: Conversational Task Workroom

Proceed with this sprint only.

Do not begin new connectors, browser extensions, local-device access, Stripe billing or unrelated platform features.

The purpose of this sprint is to transform the existing Task Centre from a one-directional task form into a sophisticated conversational workroom where users and the AI Workforce can:

* discuss ideas
* brainstorm possible work
* clarify vague requests
* recognise when a task is being proposed
* recognise when an existing task is being discussed
* refine scope before creating a task
* create tasks from conversation
* revise plans
* request and provide approvals
* ask follow-up questions
* receive live execution updates
* pause work for clarification
* review outputs
* continue discussion after completion

The conversation must understand the lifecycle of work.

It must distinguish between:

general conversation
brainstorming
possible task request
clarification required
task ready to create
task created
planning
awaiting user response
awaiting approval
approved
queued
in progress
paused
blocked
completed
failed
cancelled
follow-up on completed task

The system must not treat every message as a new task.

Core Product Experience

The intended experience is:

User:
We have an audit coming up and I am not sure where to begin.
Chief of Staff:
I can help organise that. Which registration groups are in scope, when is the audit, and where is your evidence currently stored?
User:
Core, High Intensity and Behaviour Support. The audit is next month. Most evidence is in SharePoint.
Chief of Staff:
Understood. This now looks like a formal audit-readiness task.
Proposed task:
Prepare audit readiness review for Core, High Intensity and Behaviour Support.
I recommend involving:
- Compliance Officer
- Quality Officer
- Policy Officer
Would you like me to create the task and prepare the work plan?
User:
Yes.
Chief of Staff:
Task created. I am preparing the plan now.

During execution:

Compliance Officer:
I have completed the policy register review.
Quality Officer:
I found five evidence gaps that need confirmation.
Chief of Staff:
Before continuing, I need your answer:
Are staff competency records stored in the same SharePoint location?
[Reply required]

During approval:

Chief of Staff:
The team is ready to draft corrective actions and update the audit register.
This requires Manager approval.
[Approve]
[Reject]
[Request changes]

At completion:

Chief of Staff:
The task is complete.
Outputs:
- Audit readiness report
- Evidence gap register
- Corrective action plan
Would you like the workforce to prepare the next implementation task?

Non-Negotiable Principle

The conversation is the collaboration surface.

The task remains the governed operational record.

The system must preserve:

* task state machine
* approvals
* Workforce Role assignment
* Worker Profile restrictions
* execution plans
* OpenClaw runtime submission
* tenant isolation
* permissions
* entitlements
* usage controls
* audit history

Do not replace structured tasks with ungoverned chat.

Use this relationship:

Conversation
↓
Task intent recognised
↓
Clarification and refinement
↓
User confirms task creation
↓
Formal task created
↓
Plan discussed and approved
↓
Execution updates return to thread
↓
Outputs and follow-up remain in thread

3. Task Recognition Rules

The conversation must recognise common forms of task intent.

Examples:

Can you review our incident reports?
Prepare a response to this email.
I need help getting ready for an audit.
Check which staff qualifications are expired.
Open the CRM and update the participant record.
Draft a policy review plan.
Remind the team next week.

But it must not automatically create a task for casual statements such as:

Audits are stressful.
What does the SCHADS Award say?
Tell me about restrictive practice.
I am thinking about reviewing our policies.

Use this decision model:

Informational request
→ answer in conversation
Exploratory or brainstorming request
→ discuss and refine
Clear actionable request with enough information
→ propose task creation
Clear actionable request with missing critical information
→ ask clarification
User explicitly confirms
→ create formal task

Allow organisations to configure whether low-risk tasks may be auto-created without a separate confirmation.

Default behaviour:

Require user confirmation before formal task creation.

4. Conversation State Awareness

The system must always inspect the current conversation and related task state before replying.

Examples:

No task exists

The AI may:

* brainstorm
* answer questions
* ask clarification
* propose a task

Task is draft

The AI may:

* refine scope
* revise title or description
* propose Workforce Roles
* prepare plan

Task is planning

The AI may:

* provide planning updates
* ask clarification
* revise the plan

Task is awaiting approval

The AI must:

* clearly state what is awaiting approval
* present approval card
* answer questions about the proposed action
* not imply execution has started

Task is approved or queued

The AI may:

* confirm approval
* show queue status
* explain next step

Task is executing

The AI must:

* show runtime updates
* answer status questions
* surface blockers
* ask user questions when execution cannot continue
* support pause or cancel where authorised

Task is paused or blocked

The AI must:

* explain the blocking reason
* ask the precise question required
* show what will resume after the answer

Task is completed

The AI may:

* summarise results
* show outputs
* answer follow-up questions
* propose a new follow-up task
* never reopen or alter the completed task silently

Task is failed

The AI must:

* explain the failure honestly
* show safe retry options
* preserve evidence and logs
* ask whether to retry, revise or cancel

5. Clarification Workflow

Create agent-initiated clarification requests.

A clarification request must include:

* task or proposed task
* question
* why the answer is required
* blocking or non-blocking status
* expected response type
* requested by Workforce Role
* expiry where relevant
* resolved at
* resolved by
* response

Create a structured message card.

Examples:

Clarification required
The Compliance Officer needs to know:
Which registration groups are included in this audit?
Why this matters:
The evidence checklist changes depending on registration group.
[Reply]

Execution or planning must pause where the question is blocking.

Once the user replies:

* store the response
* mark clarification resolved
* update task context
* revise the plan if necessary
* resume the correct workflow

7. Task Creation From Conversation

When the user confirms task creation:

1. validate tenant context
2. validate permission
3. validate entitlement
4. validate usage
5. create the task
6. link it to the conversation
7. link the originating messages
8. assign Workforce Roles
9. map Worker Profiles
10. create task planning state
11. add a task_created structured message
12. begin Chief of Staff planning
13. prevent duplicate creation through idempotency

The user should not have to retype the title and description into a separate form.

The existing task form may remain as an alternative.

* risks

* record the feedback
* create a revised plan version
* explain what changed
* require fresh approval where material

9. Approval Requests in Conversation

Approval requests must appear as structured cards inside the task thread.

Show:

* requested action
* requesting Workforce Role
* affected system or resource
* reason
* risk level
* before state where available
* proposed after state where available
* expiry
* approval type
* required approver

Actions:

Approve
Reject
Request changes
Ask for more information

A text reply such as:

Yes, approve it.

may be interpreted as approval intent, but deterministic permission and confirmation checks must still apply.

For high-risk approval, require explicit button confirmation even when text intent is recognised.
