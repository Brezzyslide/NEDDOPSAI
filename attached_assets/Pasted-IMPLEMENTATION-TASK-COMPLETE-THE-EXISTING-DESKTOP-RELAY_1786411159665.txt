## 1. Implement real relay token refresh

Currently `RelayClient.scheduleTokenRefresh()` ultimately calls `getAccessToken()`, but the broker implementation simply returns the static `NEEDSOPS_DEVICE_TOKEN`.

Replace this development limitation with the existing secure refresh protocol.

The connector must securely retain/use:

* deviceId
* organizationId
* accessToken
* accessTokenExpiresAt
* refreshToken
* refreshTokenExpiresAt

When the access token approaches expiry:

→ POST `/v1/devices/auth/refresh`
→ send current refresh token
→ receive rotated access + refresh token pair
→ replace old credentials
→ use new access token for relay authentication
→ securely discard old refresh token

Respect the server's existing refresh-token rotation semantics.

## 2. Do not use brokerAuthToken as relay access token

`brokerAuthToken` is NOT a relay access token.

## 4. Startup authentication lifecycle

After initial device activation has already occurred, connector startup should be capable of:

stored device identity
→ retrieve stored refresh credential
→ obtain current access token
→ start RelayClient
→ authenticate WebSocket
→ receive auth_ok
→ device becomes connected

It should NOT require a human to manually perform challenge/exchange after every restart.

If the refresh token has expired/revoked:

→ connector enters `reauthentication_required`
→ do not loop indefinitely pretending to be connected
→ require fresh activation/pairing.

## 5. Reconnect lifecycle

Prove the following:

API restart:
WebSocket closes
→ reconnect
→ authenticate with valid/current token
→ connected

Network interruption:
→ reconnect with existing backoff
→ refresh token if required
→ connected

Access-token expiry:
→ refresh
→ rotate credentials
→ continue/reconnect
→ connected

Mac connector restart:
→ load persisted credentials
→ obtain/refresh access token
→ relay connects

Device revoked:
→ stop reconnecting
→ status = revoked
