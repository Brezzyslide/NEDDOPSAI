Sprint 27.1 — Intelligent Execution Experience & Recovery

You are implementing Sprint 27.1 only.

Before writing any code:

1. Inspect the current Sprint 27 implementation.
2. Verify exactly what was completed.
3. Identify only the remaining execution experience gaps.
4. Do not rebuild completed functionality.
5. Extend the existing execution architecture.

The execution pipeline is now wired:

User Chat → Chief of Staff → Execution Intent → Approval → Execution Coordinator → Work Execution Pipeline → Completed Work → Conversation

This sprint improves the experience, resilience and transparency of that pipeline.

Part 1 — Live SSE Execution Progress

Replace database-only progress updates with real-time Server-Sent Events.

Current behaviour:

Pipeline
↓

Conversation messages written to database

↓

UI eventually sees updates

Required behaviour:

Pipeline

↓

Execution Coordinator

↓

SSE

↓

Chat updates immediately

Display live stages such as:

* Planning work…
* Building Work Package…
* Reviewing organisational knowledge…
* Consulting specialist…
* Reviewing legislation…
* Running quality review…
* Preparing completed work…
* Awaiting approval…
* Completed

Do not expose internal implementation names like manifests, execution IDs or pipelines.

Heartbeat every 15–30 seconds.

Reconnect safely without duplicate events.

Support browser refresh during execution.

Part 2 — Checkpoint-Based Clarification

Execution must never restart from the beginning after clarification.

Current:

Execution

↓

Clarification

↓

Restart

Required:

Execution

↓

Checkpoint

↓

Ask clarification

↓

Persist state

↓

Resume from checkpoint

Persist:

* Current stage
* Retrieved knowledge
* Built work package
* Execution context
* Partial outputs
* Specialist state

Resuming should continue from the last successful checkpoint.
