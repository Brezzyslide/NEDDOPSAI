SPRINT 29A — Unified Execution Architecture & Resource Resolution Design

This is an ARCHITECTURE sprint.

Do NOT implement code.

Do NOT modify any files.

Do NOT create migrations.

The objective is to design the next-generation execution architecture for NeedsOps before implementation.

Everything must align with the long-term vision of NeedsOps as a cloud-first professional workforce platform with an optional desktop extension (NeedsOps Connector).

==================================================
BACKGROUND
==================================================

The current inspection identified several architectural gaps:

• Two specialist execution models exist.
• EvidencePack only exists in one execution path.
• Desktop Connector capability exists largely as placeholders.
• Knowledge Resolution only retrieves organisation knowledge.
• There is no routing for connector-based resource requests.
• OpenClaw remains an internal runtime but is not fully utilised.

We are NOT looking for isolated fixes.

We are redesigning the execution architecture while preserving backwards compatibility where appropriate.

==================================================
ARCHITECTURAL PRINCIPLES
==================================================

The following principles are mandatory.

1.

There must be ONE specialist execution model.

Conversation execution and task execution must converge into a single execution pipeline.

There should never be two different runtime contexts for specialists.

Every specialist should always receive:

• Professional DNA
• Runtime Manifest
• Resource Plan
• Resource Package
• Organisation Memory
• Conversation Context
• Blueprint (where applicable)

2.

Chief of Staff remains the orchestrator.

The Chief of Staff is responsible for:

• understanding intent
• selecting specialists
• determining required resources
• planning execution
• delegating work

No new orchestration layer should replace the Chief of Staff.

3.

OpenClaw remains an INTERNAL runtime.

Customers never interact with or see OpenClaw.

The customer-facing product is:

NeedsOps Connector

The connector internally uses OpenClaw to execute local capabilities.

4.

Knowledge Resolution must evolve into Resource Resolution.

It should become capable of obtaining resources from multiple providers rather than only the organisation knowledge library.

==================================================
RESOURCE PROVIDERS
==================================================

The design must support providers including:

• Organisation Knowledge
• Organisation Memory
• Task Uploads
• NeedsOps Connector
• Trusted Public Sources
• Future Cloud Providers
    - SharePoint
    - OneDrive
    - Google Drive
    - Confluence
    - Notion
    - others

The architecture must allow future providers without redesign.

==================================================
IMPORTANT DESIGN RULE
==================================================

Desktop access must NOT only occur when evidence is missing.

Example:

User:

"Go to my desktop and review Medication Policy.docx."

The system must honour the requested resource location immediately.

Likewise:

"Save this completed work into Documents."

should invoke the connector directly.

Resource selection is driven by BOTH:

• user intent

AND

• execution requirements.

==================================================
RESOURCE PLAN
==================================================

Investigate introducing a Resource Plan generated by the Chief of Staff.

Example:

Required Resources

• Medication Policy
• NDIS Practice Standards
• Behaviour Support Plan

Preferred Providers

• Desktop Connector
• Trusted Public Sources

The Resource Plan should be passed through execution.

==================================================
RESOURCE PACKAGE
==================================================

Investigate replacing or extending EvidencePack.

The new model should support mixed resource origins.

Possible examples:

Organisation Knowledge

Organisation Memory

Task Uploads

Connector Resources

Trusted Sources

Generated Runtime Notes

Determine whether:

• EvidencePack should evolve

OR

• ResourcePackage should replace it

Recommend the better architecture.
