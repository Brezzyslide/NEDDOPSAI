SPRINT 29L — FULL PRODUCT MODULE, SUBMENU & FUNCTION OVERLAP AUDIT

THIS IS AN INVESTIGATION / ARCHITECTURE AUDIT ONLY.

DO NOT IMPLEMENT, REFACTOR, DELETE, RENAME OR MOVE ANYTHING.

I want a complete audit of the NeedsOps AI+ product from the USER-FACING MODULE level down to the actual backend services.

The concern is that as the platform has grown, we may now have:

- modules that overlap
- different screens exposing the same underlying function
- duplicated workflows
- duplicated outputs
- modules that appear connected in the UI but are not technically wired end-to-end
- old/dead screens or legacy routes
- multiple ways of creating the same Completed Work
- unclear ownership between Chat, Tasks, Active Work, Operations Centre, Workforce, Inbox and Completed Work
- unnecessary complexity that could slow the product or confuse users

Do not assume something works because a component, route, service or test exists.

Trace the real execution path.

PART E — DUPLICATED FUNCTION AUDIT
==================================================

This is extremely important.

Look for cases where two or more modules perform the same business function.

Examples to investigate, but do not assume:

Chat vs Tasks
Chat vs Workforce execution
Tasks vs Active Work
Active Work vs Operations Centre
Operations Centre vs Workforce
Inbox vs Notifications
Dashboard vs Operations Centre

Build a duplication matrix:

Function
Module A
Module B
Same backend service?
Same DB record?
Same output?
Intentional alternate entry point?
True duplication?
Recommendation

Distinguish between:

1. SAME CAPABILITY, DIFFERENT ENTRY POINT

This may be desirable.

Example:
A user asks for a policy review through Chat or creates it explicitly through Tasks, but both eventually use the same execution engine.

That is NOT necessarily duplication if there is one canonical backend workflow.

2. DUPLICATED IMPLEMENTATION

Two separate services implement essentially the same business process.

This is technical debt.

3. DUPLICATED OUTPUT

Two modules independently create records/documents representing the same completed piece of work.

This is potentially dangerous.

4. DUPLICATED UI

Two screens expose almost identical information without a clear reason.

This may create user confusion even if the backend is shared.

==================================================

1. normal lightweight execution
2. specialist execution
3. knowledge retrieval
4. claim emission
5. evidence persistence
6. semantic claim validation
7. absence verification
8. Completed Work approval workflow

"Review our Complaints Management Policy against our organisational requirements."

The first should normally NOT need:
