# NeedsOps AI+

## Sprint 9.2 — Tenant-Aware Chief of Staff Memory

Continue from the existing OpenAI-enabled Chief of Staff and Conversational Task Workroom.

The objective of this sprint is to make the Chief of Staff genuinely tenant-aware and reliable across long-running conversations.

The Chief of Staff must retain and retrieve approved information about each organisation while preserving strict tenant isolation.

It must be capable of reviewing up to 300 previous conversation messages when building context.

However, it must not blindly send all 300 messages to the model on every request.

Use intelligent retrieval, summarisation and token budgeting.

Do not change unrelated platform functionality.

---

# Core Objective

The Chief of Staff should understand:

* which organisation it is serving
* how that organisation operates
* relevant organisational preferences
* previous decisions
* unresolved questions
* current tasks
* current approvals
* previous conversation context
* relevant internal terminology
* relevant connected systems
* known constraints

The Chief of Staff must not mix information between organisations.

Use this context architecture:

```text
Chief of Staff base instructions
+
Tenant profile
+
Tenant approved memory
+
Conversation rolling summary
+
Pinned decisions
+
Unresolved questions
+
Relevant historical messages
+
Recent messages
+
Current task state
+
Current approvals
```

---

# Important Principle

The Chief of Staff must remain stateless at the server-process level.

Do not create a long-lived in-memory Chief of Staff object.

All durable memory must be stored in PostgreSQL or another approved persistent store.

Each AI request should reconstruct the required context from durable tenant-scoped data.

This preserves:

* horizontal scalability
* restart recovery
* tenant isolation
* auditability
* predictable memory behaviour

# 3. Read Up to 300 Previous Messages

Update the conversation context service.

It must be capable of retrieving up to:

```text
300 previous messages
```

from the current tenant-scoped conversation.

Make the limit configurable:

```env
AI_MAX_HISTORY_MESSAGES=300
AI_RECENT_HISTORY_MESSAGES=30
AI_CONTEXT_TOKEN_BUDGET=
AI_MEMORY_SUMMARY_THRESHOLD=40
```

Do not hard-code the old 20-message limit.

Important behaviour:

1. Read up to 300 historical messages from PostgreSQL.
2. Always include the most recent configurable message window.
3. Use the rolling conversation summary for older messages.
4. Retrieve specific older messages when they are relevant to the current request.
5. Respect the model context and configured token budget.
6. Never truncate recent messages without recording that truncation occurred.
7. Never send messages from another organisation.

Do not interpret “300 messages” as permission to send all 300 raw messages on every AI call.

The Chief of Staff LLM service must consume this package rather than directly reading the last 20 messages.

# 5. Relevance Retrieval

Implement deterministic relevance selection first.

Use:

* keywords
* task references
* participant references
* explicit message links
* related task IDs
* message types
* pinned decisions
* unresolved questions
* timestamps
* current message intent

If an approved semantic search or embedding architecture already exists, it may be used behind a provider-independent interface.

Do not make a vector database mandatory for this sprint unless it already fits the architecture cleanly.

The retrieval service should favour:

1. current task information
2. unresolved blocking questions
3. approved decisions
4. recent messages
5. messages directly related to the current request
6. relevant organisation memory
7. older background discussion

---

# 6. Rolling Summarisation

Create a rolling summarisation service.

When conversation messages exceed the configured threshold:

1. identify messages not yet included in the current summary
2. generate an updated structured summary
3. preserve source message references
4. update `summarised_through_message_id`
5. increment the summary version
6. keep the original messages unchanged
7. audit the summarisation event

The summary must never silently replace the original conversation record.

Use the AI Privacy Gateway for summary generation.

Provide deterministic fallback where possible.

Summaries must preserve:

* decisions
* unresolved questions
* approvals
* commitments
* scope
* task links
* important constraints
* relevant people and systems

Avoid storing chain-of-thought or hidden reasoning.

Store conclusions and operational facts only.

# 7. Pinned Decisions

Allow users and authorised Workforce Roles to pin important decisions.

Examples:

```text
The audit covers Core, High Intensity and Behaviour Support.

Mary approves all external compliance submissions.

SharePoint / Governance / Approved Policies is the authoritative policy folder.
```

Create:

* pin decision
* edit pin
* unpin
* show source message
* show who pinned it
* audit every change

The Chief of Staff should prioritise pinned decisions over inferred conversation summaries.

When two pinned decisions conflict, do not guess.

Create a contradiction warning and ask the user to resolve it.

# 8. Organisation Memory Approval

The Chief of Staff may propose organisation memories based on repeated conversation facts.

Example:

```text
Proposed organisation memory:

“External compliance reports require approval from the General Manager.”

Source:
Conversation 147, messages 22 and 31.

[Approve]
[Reject]
[Edit]
```

The AI may propose memory.

NeedsOps and an authorised human decide whether it becomes approved memory.

Do not automatically save inferred sensitive facts as authoritative organisation memory.

---

# 9. Memory Conflict Detection

Create deterministic conflict checks.

Detect:

* two current approval rules naming different approvers
* superseded policy references
* contradictory reporting lines
* conflicting dates
* conflicting task scope
* expired memory
* unapproved memory being used as fact

Return structured warnings such as:

```text
I found conflicting information about who approves payroll submissions.

Earlier decision:
Finance Manager

Current message:
Chief Executive Officer

Please confirm which rule is current.
```

The Chief of Staff must ask rather than choose silently.

# 10. Memory Source and Confidence

Every memory supplied to the Chief of Staff should carry:

* source
* status
* confidence
* effective date
* expiry
* authority level

Suggested authority order:

```text
approved organisation memory
pinned human decision
current approved policy
current task record
current approval record
recent user message
conversation summary
unconfirmed AI inference
```

Lower-authority data must not silently override higher-authority data.

---

# 11. Tenant Isolation

Every memory query must require:

* organization_id
* authenticated user
* active local membership
* purpose authorisation

Add RLS to all new memory tables.

The application must fail closed when tenant context is missing.

Create tests proving:

* Tenant A cannot read Tenant B memory.
* Tenant A cannot search Tenant B messages.
* Tenant A summary cannot include Tenant B content.
* Cross-tenant source IDs are rejected.
* Platform staff do not automatically receive conversation memory access.
* AI requests never contain another tenant’s memory.

# 16. Scalability

Memory reconstruction must work across multiple API instances.

Do not use process-local memory as the source of truth.

The architecture must support:

```text
stateless API instances
+
PostgreSQL durable memory
+
future Redis cache
+
future queue workers
```

Caching may be introduced behind an interface, but the database remains authoritative.

Avoid one database query per message when a bulk query can be used.

Add indexes for:

* organization_id
* conversation_id
* status
* memory_type
* importance
* updated_at
* source_id
* summarised_through_message_id

# 17. Usage and Cost Controls

Record:

* messages retrieved
* messages sent to AI
* summary token count
* recent-message token count
* historical retrieval token count
* organisation-memory token count
* total context token estimate
* summarisation requests
* summarisation cost estimate

Do not let a 300-message conversation cause uncontrolled token usage.

Use configurable context budgets.

When the context exceeds budget:

1. preserve system rules
2. preserve current task state
3. preserve pinned decisions
4. preserve unresolved questions
5. preserve recent messages
6. summarise or omit lower-priority history
