Give Replit this as the instruction for the next major build sprint:

Proceed immediately with the NeedsOps Enterprise Data Isolation, Privacy and Organisation Database implementation.

Do not provide another architecture review, proposal or gap analysis. The current-state assessment has already been accepted.

Your task is to fix the current tenant-isolation vulnerabilities first, then implement the approved organisation-specific database architecture, AI Privacy Gateway, audit separation, secure connector framework and all privacy controls described below.

This work must preserve the current application while moving NeedsOps from a shared application-controlled tenant model to a secure hybrid database architecture.

Overall Objective

Build NeedsOps so that:

1. The current shared database is immediately protected by PostgreSQL Row Level Security.
2. Every organisation receives its own separately provisioned Operational Database.
3. Clinical, disability, workforce and operational information never enters the shared Platform Database.
4. The Platform Console cannot casually browse customer operational content.
5. Every AI request is tenant-scoped, permission-aware, purpose-limited and auditable.
6. Connector credentials and connected-system data remain isolated to the organisation that owns them.
7. Cross-organisation data access is prevented at the application, database, AI, background-job and connector layers.
8. Existing organisations are safely migrated without data loss or unacceptable disruption.

Non-Negotiable Security Rule

NeedsOps is a shared platform, but every customer organisation must operate as though it has its own private enterprise environment.

No organisation may read, update, delete, search, embed, summarise, export or infer information belonging to another organisation.

A valid organisation slug is not proof of access.

Application WHERE clauses are not sufficient as the only isolation control.

Prompt instructions telling AI to respect privacy are not sufficient as a security control.

Security must be enforced technically through authentication, authorisation, database boundaries, Row Level Security, tenant-aware data access, audit logging and automated isolation testing.

Phase 1: Immediately Fix the Current Shared Database Vulnerabilities

Implement this first before building additional operational modules.

1. PostgreSQL Row Level Security

Enable PostgreSQL Row Level Security on every current tenant-owned table.

RLS must apply to:

* SELECT
* INSERT
* UPDATE
* DELETE

The authorised organisation context must be established from the authenticated user and verified membership, not directly from a URL parameter, request body, query parameter or organisation slug.

Use a secure transaction-scoped PostgreSQL tenant context such as:

SET LOCAL app.current_organization_id = '<verified-organisation-id>';
SET LOCAL app.current_user_id = '<authenticated-user-id>';

RLS policies must compare records against the verified database session context.

The application must not connect using a role that can casually bypass RLS.

Any controlled RLS bypass role must be limited to narrowly defined migration or platform maintenance operations and must never be used by ordinary application routes.

2. Fix Tables Without Direct Organisation Ownership

Add a non-null organization_id to:

* approval_history
* task_execution_plans
* task_specialists

Requirements:

* Backfill existing records from their valid parent relationships.
* Identify and report orphaned or ambiguous records.
* Add foreign keys.
* Add indexes.
* Prevent null organisation ownership.
* Add database constraints where practical to ensure the child organisation matches the parent organisation.
* Apply RLS directly to these tables.
* Do not rely only on joins to infer organisation ownership at query time.

Review all other tables for the same weakness and fix any additional tables lacking direct tenant ownership.

3. Replace Slug-Based Tenant Trust

Refactor resolveTenantFromSlug.

The required request sequence is:

Authenticate user
→ Resolve requested organisation
→ Verify active user-to-organisation relationship
→ Verify organisation status
→ Establish authorised organisation context
→ Establish authorised user context
→ Apply role and permissions
→ Establish PostgreSQL RLS context
→ Execute request

The organisation slug may identify the requested organisation, but it must never grant access.

Do not accept organization_id, tenantId or equivalent values supplied by the browser as trusted authorisation context.

4. Central Tenant-Aware Data Access

Create a central tenant-aware database access layer.

Ordinary services and route handlers must not freely access tenant tables using the unrestricted database client.

Provide secure interfaces such as:

withPlatformContext()
withTenantContext()
withUserTenantContext()
withSystemTenantContext()

Each interface must:

* require explicit identity and purpose
* validate the organisation
* set the database context
* open a transaction where required
* prevent context leakage between pooled connections
* clear or isolate context after execution
* produce an audit event
* fail closed if no tenant context exists

Any tenant query attempted without authorised tenant context must fail.

Phase 9: AI Privacy Gateway

Build an AI Privacy Gateway in front of every model request.

No module may send customer information directly to an AI provider without going through the gateway.

The gateway must:

1. Authenticate the user.
2. Verify the user’s organisation.
3. Verify active organisation membership.
4. Connect only to that organisation’s Operational Database.
5. Apply the user’s local roles and permissions.
6. Confirm the purpose of the request.
7. Retrieve only the minimum information necessary.
8. Exclude information outside the user’s access.
9. Redact or mask unnecessary sensitive information.
10. Record the records and document categories accessed.
11. Apply organisation-specific AI settings.
12. Apply provider and model restrictions.
13. Send only approved context to the model.
14. validate the response before release.
15. Apply human approval requirements.
16. Record an AI audit event.
17. Apply retention rules.
18. Prevent cross-organisation memory or retrieval.

The model must never decide its own permissions.

The model must receive only information already authorised by the gateway.

AI Identity Propagation

Every AI request must carry:

* organisation ID
* user ID
* operational role
* permission set
* purpose
* initiating module
* participant or record scope where applicable
* correlation ID
* approval requirement
* retention classification

Purpose Limitation

Supported purposes may include:

* drafting a case note
* summarising authorised incidents
* preparing a weekly report
* locating an approved procedure
* comparing authorised records
* assisting with compliance documentation
* drafting an authorised care-related document

Requests without a legitimate operational purpose must be denied or escalated.

Minimum-Necessary Retrieval

The AI must not retrieve every record merely because the user has broad access.

Retrieve only what is reasonably necessary for the task.

For example, rostering assistance should not automatically retrieve trauma history, medication records or forensic information where those details are not needed.

Retrieval, Not General Training

Organisation information must not be used for general model training.

Customer information may be retrieved temporarily to perform an authorised task under the organisation’s settings and provider agreement.

Store prompts, responses and retrieved context only according to configured retention rules.

Human Approval Gates

Require authorised human review before AI outputs become official records or trigger high-risk actions, including:

* behaviour support plans
* restrictive practice documentation
* incident classifications
* clinical recommendations
* medication-related decisions
* external regulatory submissions
* legal or compliance determinations
* participant risk decisions
* staff disciplinary decisions
* automated access revocation
* material financial actions

The AI may draft and assist. It must not independently make regulated decisions.
