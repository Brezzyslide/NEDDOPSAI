WEBSOCKET SERVER REQUIREMENTS
────────────────────────────────────────

Add a relay endpoint such as:

wss://<api-host>/v1/devices/relay

or another route consistent with the existing API architecture.

Do not require a device ID in the URL unless the authentication model safely validates it.

On connection:

1. Device presents a short-lived access token
2. Server validates:
   - token signature
   - device status
   - organisation
   - expiry
   - revocation state
   - token audience
3. Server associates the socket with the device
4. Server marks the device as connected
5. Server records:
   - connected_at
   - last_seen_at
   - app version
   - OS
   - architecture
   - transport type
6. Server sends the current configuration version
7. Device acknowledges readiness

Support message types such as:

- auth

- task_dispatch
- task_ack
- task_progress
- task_result
- task_error
- config_update
- reconnect_required
- token_expiring
- device_revoked
- shutdown

  "deviceId": "...",
  "timestamp": "...",
  "payload": {}
}

TASK DELIVERY AND IDEMPOTENCY
────────────────────────────────────────

Implement:

- unique task execution ID
- device acknowledgement
- task status transitions
- delivery attempt counter
- sent_at
- acknowledged_at
- started_at
- completed_at
- failed_at
- result reference
- error code
- last delivery error

If a device disconnects before acknowledging a task:

- return it to a pending or retryable state
- retry only according to policy
- do not execute duplicates silently

If a duplicate task arrives:

- identify it by execution ID
- return the previously known state or result
- do not execute twice

Do not persist sensitive business payloads longer than necessary.

PHASE 2 — SHORT-LIVED DEVICE AUTHENTICATION
────────────────────────────────────────

The current implementation uses long-lived device credentials with a 90-day rotation date.

Replace or upgrade this model.

Required model:

- device identity based on local public/private key pair
- short-lived access token
- refresh mechanism or signed challenge flow
- revocation
- rotation
- audit events

Preferred access-token lifetime:

- 10 to 30 minutes

Refresh credentials must:

- be device-specific
- be revocable
- be rotated on use where practical
- be stored only in secure OS storage
- never be written in plaintext configuration
- be hashed in the database where applicable

Alternative acceptable approach:

- device signs a server-issued nonce with its private key
- server validates the registered public key
- server issues a new short-lived access token

Implement one clear model rather than mixing several incomplete approaches.

Required endpoints may include:

- POST /v1/devices/auth/challenge
- POST /v1/devices/auth/exchange
- POST /v1/devices/auth/refresh
- POST /v1/devices/:id/revoke

On revocation:

- close the current WebSocket
- reject future token refresh
- reject future challenge exchange
- mark the device revoked in the portal
- write an audit event

Add automated tests for:

- valid token
- expired token
- wrong audience
- wrong device
- revoked device
- refresh rotation
- reused refresh credential
- invalid signature
- changed public key
- concurrent refresh attempt
