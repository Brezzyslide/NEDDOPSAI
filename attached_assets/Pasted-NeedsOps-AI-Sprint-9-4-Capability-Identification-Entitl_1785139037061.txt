NeedsOps AI+

Sprint 9.4 — Capability Identification, Entitlement Enforcement and Upgrade Guidance

Continue from the current Chief of Staff, organisation memory, Workforce Pack and entitlement architecture.

The objective of this sprint is to ensure that every user request is classified into one or more required business capabilities before any specialist is assigned or any task is created.

The Chief of Staff must recognise when an organisation requests work outside the capabilities included in its subscription.

When a required capability is not purchased, the Chief of Staff must respond helpfully and politely, explain the boundary, offer any permitted partial assistance, and surface the correct upgrade path.

Do not rely only on prompt wording.

Capability access must be enforced deterministically by NeedsOps services.

The AI identifies likely intent and capabilities.

NeedsOps validates and decides access.

⸻

Core Flow

Implement this flow:

User request
↓
Chief of Staff understands intent
↓
Required business capabilities identified
↓
Capabilities validated against registry
↓
Organisation entitlements checked
↓
Available capabilities routed to specialists
↓
Unavailable capabilities blocked
↓
Chief of Staff explains the limitation and upgrade path

No task, specialist run, execution package or OpenClaw submission may proceed for an unavailable capability.

⸻

Product Principle

NeedsOps sells access to business capabilities through plans, Workforce Packs and add-ons.

The customer is not buying unrestricted use of a named AI agent.

A Workforce Role may only perform work within:

* its registered capabilities
* its Worker Profile
* the organisation’s entitlements
* the user’s permissions
* current usage allowances
* required approvals

A Compliance Officer must not perform accounting simply because the user asks it to.

3. Capability Identification Service

Create a provider-independent service such as:

interface CapabilityIdentificationService {
  identifyCapabilities(input: {
    organizationId: string;
    userId: string;
    conversationId?: string;
    taskId?: string;
    message: string;
    conversationContext: ConversationContext;
  }): Promise<CapabilityIdentificationResult>;
}

Suggested result:

interface CapabilityIdentificationResult {
  understoodIntent: string;
  requestedCapabilities: Array<{
    capabilityCode: string;
    requestedLevel:
      | "general_information"
      | "professional_analysis"
      | "execution";
    confidence: number;
    reason: string;
    required: boolean;
  }>;
  ambiguous: boolean;
  clarificationQuestions: string[];
}

The LLM may propose capability codes.

NeedsOps must filter all capability codes against the canonical registry.

Invented capabilities must be rejected.

4. Deterministic Capability Validation

After capability identification, validate:

1. capability exists
2. capability is active
3. requested level is valid
4. capability belongs to an eligible Workforce Pack
5. at least one Workforce Role can perform it
6. Worker Profile permits the requested level
7. required execution channel is valid
8. required connector category is valid

Return a structured validation result.

Use the existing:

Do not call Stripe.

6. Three-Level Access Model

Implement the following default behaviour.

General Information

Example:

What is a BAS?
What does payroll reconciliation mean?
What is an incident register?

General educational answers may be provided where safe, even if the organisation does not own the corresponding Workforce Pack.

The response must remain general.

It must not use restricted organisation records or present itself as completed professional work.

Professional Analysis

Example:

Review our BAS records.
Analyse our payroll against SCHADS.
Review our audit evidence.

Requires the relevant Workforce Pack and capability entitlement.

Execution

Example:

Prepare and lodge our BAS.
Update payroll records.
Submit the incident form.
Create invoices in Xero.

Requires:

* relevant Workforce Pack
* execution-level capability
* required execution-channel entitlement
* connector eligibility
* usage allowance
* Worker Profile permission
* human approval where required
* live runtime availability

7. Mixed-Capability Requests

Support requests requiring multiple capabilities.

Example:

Review overtime compliance and calculate the financial impact.

Identified capabilities:

payroll.schads_analysis
finance.cost_impact_analysis

If the organisation owns Compliance but not Finance:

* complete or propose the permitted compliance part
* block the finance analysis
* explain the split clearly
* offer the relevant upgrade
* do not present a partial result as complete

Suggested result structure:

interface MixedCapabilityDecision {
  allowedCapabilities: CapabilityAccessDecision[];
  blockedCapabilities: CapabilityAccessDecision[];
  canProceedPartially: boolean;
  requiresUserConfirmationForPartialWork: boolean;
}

Default behaviour:

Ask the user before creating a partial task when a material part is unavailable.

8. Chief of Staff Response Behaviour

The Chief of Staff response must be useful, calm and commercially clear.

Do not use hostile wording such as:

Access denied.
You cannot use this agent.
Payment required.

Use wording such as:

That request requires the Finance Workforce Pack, which is not currently included in your organisation’s plan.
I can still explain the process at a general level, or I can complete the compliance portion of the request.
To analyse or prepare the financial component using your organisation’s records, a Finance Workforce upgrade is required.

For a fully blocked execution request:

I cannot prepare or submit the BAS under the current plan.
That work requires:
- Finance Workforce Pack
- Accounting execution capability
- an approved accounting connector or browser session
I can still help you outline the required documents and explain the process.

The response should include:

* what was requested
* which capability is required
* what access is currently available
* what part, if any, can still be completed
* which Workforce Pack or add-on is required
* upgrade or trial action
* no false claim that work started

10. Task Creation Gate

Before creating a formal task from conversation:

1. identify capabilities
2. validate capability codes
3. evaluate access for each capability
4. determine full, partial or blocked access
5. ask clarification where capability intent is ambiguous
6. obtain user confirmation for material partial work
7. create only permitted task scope
8. store blocked capability requirements on the task proposal
9. prevent unavailable specialists from being assigned

Do not create tasks that contain prohibited or unavailable execution steps.

⸻

11. Specialist Routing Gate

The Chief of Staff must route only to specialists eligible for the allowed capabilities.

Example:

Prepare BAS

accounting.bas_preparation

Accounts Officer
Financial Reporting Officer
Organisation access:
Finance Workforce not included
Result:
No specialist run created

The Compliance Officer must not be selected as a substitute.

Do not select the closest available agent merely to avoid an upgrade message.

12. Specialist Run Gate

Before creating a specialist run, validate:

* capability entitlement
* capability level
* Workforce Pack
* role capability mapping
* Worker Profile
* usage
* subscription state
* approval requirement
* runtime availability where execution is requested

Store the capability decision ID on the specialist run.

No specialist run may exist without an authorised capability decision.

13. OpenClaw Gate

Before generating or submitting an OpenClaw handoff package:

* validate execution-level capability
* validate execution channel
* validate connector eligibility
* validate Worker Profile
* validate approval
* validate runtime
* validate usage
* validate package expiry

A general-information or professional-analysis entitlement must never become execution access automatically.
